# GitLab Epic MCP (TypeScript Only)

## Goal

Extend `@zereight/mcp-gitlab` with a **small custom MCP server** that adds only:

- `create_epic`
- `get_epic`

This design works with **GitLab CE/Open Source** using a **virtual epic model**.

Instead of native GitLab Premium Epics:

```text
GitLab Premium:
Epic (native object)
```

We implement:

```text
GitLab CE/Open Source:
Epic -> GitLab Issue(label=epic)
```

Example:

```text
[EPIC] Client Authentication
label: epic
```

---

# High Level Architecture

```text
AI Agent / MCP Client
        |
        | tool call
        v
+---------------------------+
|  @zereight/mcp-gitlab     |
|  Existing GitLab tools    |
|  (issues, labels, MR)     |
+---------------------------+
        |
        +----------------------+
                               |
                               v
+----------------------------------------------+
| Custom MCP: gitlab-epic-mcp                  |
|                                              |
| create_epic()                                |
| get_epic()                                   |
+----------------------------------------------+
                 |
                 v
+----------------------------------------------+
| GitLab REST API (@gitbeaker/rest)            |
+----------------------------------------------+
```

# Layer Responsibilities

## 1. index.ts

Purpose:

MCP entry point.

Responsibilities:

- start MCP server
- register tools
- route tool requests

Registered tools:

```ts
create_epic
get_epic
```

Mental model:

```ts
const tools = {
  create_epic,
  get_epic
};
```

This acts as the MCP router/controller.

---

## 2. config/env.ts

Purpose:

Centralized environment validation.

Example:

```ts
export const env = {
  gitlabUrl: process.env.GITLAB_URL!,
  gitlabToken: process.env.GITLAB_TOKEN!
};
```

Benefits:

- single source of truth
- avoids repeated env lookups
- easier testing

---

## 3. clients/gitlabClient.ts

Purpose:

Reusable GitLab API client.

Example:

```ts
import { Gitlab } from "@gitbeaker/rest";

export const gitlab = new Gitlab({
  host: process.env.GITLAB_URL,
  token: process.env.GITLAB_TOKEN
});
```

Why?

Avoids this anti-pattern:

```ts
new Gitlab(...)
new Gitlab(...)
new Gitlab(...)
```

Instead:

```text
single shared client
```

---

## 4. schemas/epic.schema.ts

Purpose:

Validate MCP tool input.

Use `zod`.

Example:

```ts
import { z } from "zod";

export const createEpicSchema = z.object({
  projectId: z.number(),
  title: z.string(),
  description: z.string().optional()
});
```

Benefits:

- prevents bad requests
- runtime validation
- type safety

---

## 5. tools/

Purpose:

Expose MCP tools to the AI agent.

These are thin wrappers.

Responsibilities:

- receive MCP request
- validate input
- call service layer
- return formatted response

Should remain thin.

Bad:

```ts
tool = 200 lines logic
```

Good:

```ts
tool -> service
```

---

## 6. services/epicService.ts

Purpose:

Business logic for epic operations.

Contains:

### createEpic()

Responsibilities:

- apply naming convention
- add epic label
- create GitLab issue

Transform:

```text
Client Authentication
```

Into:

```text
[EPIC] Client Authentication
```

with label:

```text
epic
```

Then create issue in GitLab.

---

### getEpic()

Responsibilities:

- retrieve GitLab issue
- verify epic label exists
- return normalized response

Example response:

```json
{
  "epicId": 123,
  "title": "[EPIC] Client Authentication",
  "description": "Client onboarding flow",
  "labels": ["epic"],
  "webUrl": "https://gitlab..."
}
```

---

## 7. utils/markdown.ts

Purpose:

Reusable markdown generation.

Example:

```ts
export function buildEpicDescription() {
   return `
## Objective
TBD

## Scope
TBD
`;
}
```

Keeps markdown templates out of service logic.

# Runtime Flow

## create_epic()

Prompt:

```text
Create epic Client Authentication
projectId=10
```

Execution:

```text
AI Agent
    |
    v
create_epic()
    |
    v
index.ts
    |
    v
tools/createEpic.ts
    |
    v
services/epicService.ts
    |
    v
gitlabClient.ts
    |
    v
GitLab REST API
    |
    v
GitLab issue created
```

Result:

```text
[EPIC] Client Authentication
label: epic
```

---

Prompt:


Execution:

```text
AI Agent
    |

get_epic()

    v
index.ts
    |
    v
tools/getEpic.ts
    |
    v
services/epicService.ts
    |
    v
gitlabClient.ts
    |
    v
GitLab REST API
```

Returns:

```json
{
  "epicId": 123,
  "title": "[EPIC] Client Authentication",
  "status": "opened"
}
```

# Why This Structure

You only need:

```text
create_epic
get_epic
```

So keep architecture minimal.

Avoid overengineering.

Good balance:

```text
Tool Layer
    ↓
Service Layer
    ↓
GitLab Client
```

This keeps implementation clean while remaining easy to extend later if needed.
