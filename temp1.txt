## 1. System Glossary

| Short Name | Long Form | Role / Purpose |
|------------|-----------|----------------|
| **CROP** | Client Report Ordering Platform | **Main system under development.** Orchestrates scheduling, batch processing, price readiness checks, payload requests, document generation triggers, retrigger, and delivery channel management. |
| **CRDS** | Client Reporting Data Services | Provides the document payload (positions, balances, transactions, NAV) needed to generate a document for a given portfolio + period. Acts as the data assembly layer. |
| **LIPL** | Local Integration Provision Layer | Provides delivery instructions per portfolio: frequency of statement delivery, mailing address, preferred language, and currency. |
| **CRM** | Customer Relationship Management System | Source of truth for client static data. Provides list of portfolios and their association with clients, entity type (Bank/JV), and document applicability flags. |
| **OMOS** | Output Management Orchestra System | Receives portfolio + payload from CROP; generates PDF documents; surfaces them to users for review; manages release to output channels (eDoc, Printer, Archive). |
| **GSM** | Global Securities Master (Data Warehouse) | Master data and price warehouse. Feeds daily prices for standard instruments and is the landing zone for operations-uploaded prices for structured bonds and funds. Downstream feeds CRDS. |
| **eDoc** | Client eDocuments System | Electronic document delivery channel for distributing statements to clients digitally. |
| **JWM** | Japan Wealth Management | Business domain in scope. Has two legal entities: JWM Bank (Bank entity) and JWM Securities (JV entity). |
| **ME+N** | Month-End Plus N Days | Refers to batch run days after month-end close: ME+1, ME+2, ME+3, ME+4. |

## 2. Identified Gaps & Critical Issues

### 2.1 Business Logic Gaps

| # | Gap | Severity | Description & Risk |
|---|-----|----------|--------------------|
| **G1** | Price Staleness Threshold Not Defined | 🔴 HIGH | The system accepts "older than month-end" prices via user acceptance, but there is no defined threshold (e.g., price must not be older than X days). Without this, all historical prices could theoretically be accepted, which is a business integrity risk. |
| **G2** | "Active Portfolio" Definition Missing | 🔴 HIGH | CROP must filter only active portfolios, but the source of the "active" flag is not defined. Is it in CRM? CRDS? A local CROP config table? If it comes from CRM, does CRM have a real-time active/inactive API? |
| **G3** | LIPL vs CROP Frequency Conflict | 🔴 HIGH | LIPL provides delivery frequency per portfolio. CROP also defines schedule for balance certificates. When both systems have a frequency configured, the resolution rule is not defined. This must be an explicit business decision. |
| **G4** | Idempotency of Batch Runs | 🔴 HIGH | If ME+2 batch runs, fails midway, and is re-triggered, the logic for skipping already-processed portfolios is not defined. Without idempotency, duplicate document generation is a real risk. |
| **G5** | Partial CRDS Payload Failures | 🔴 HIGH | If CRDS returns payload for 900/1000 portfolios and times out for 100, does the batch proceed for the 900? Are the 100 retried immediately or in the next ME+N run? No stated error handling strategy. |
| **G6** | OMOS Document Rejection Workflow | 🟠 MEDIUM | OMOS shows documents for review before release. What happens if a reviewer rejects a document? Is a regeneration triggered in CROP? Does it re-enter the SCHEDULED state? This workflow is missing. |
| **G7** | Ad-hoc Price Bypass Scope & Governance | 🟠 MEDIUM | Ad-hoc requests bypass price checks — this is stated but not governed. Should all users bypass price check on ad-hoc, or only privileged roles? Should a warning/watermark exist on ad-hoc documents to differentiate from periodic ones? |
| **G8** | Price Upload Validation (GSM) | 🟠 MEDIUM | Operations upload structured bond/fund prices into GSM via file upload. There is no mention of validation rules (price range checks, duplicate upload prevention, approval before propagation to CRDS). Erroneous prices could silently corrupt statements. |
| **G9** | Multi-Language Document Handling | 🟡 LOW | LIPL provides language per portfolio. It is unclear whether CRDS payload is language-aware or whether OMOS handles language rendering. This must be clarified to prevent all documents defaulting to a single language. |
| **G10** | Suppression Rules | 🟡 LOW | No mention of whether certain portfolios or clients can be excluded from statement generation (e.g., dormant accounts, client opt-outs, litigation holds). This is a common wealth management requirement. |
| **G11** | Bank vs JV Portfolio Overlap | 🟠 MEDIUM | Can a single portfolio ID exist in both Bank and JV entities? If yes, entity scoping in CROP (batch, document state, price check) must always include entity as a discriminator key — this is architecturally critical. |
| **G12** | Notification & Alerting | 🟠 MEDIUM | No alerting mechanism defined for: batch failures, price staleness counts exceeding threshold, CRDS/OMOS integration failures. Operations will have no visibility without this. |

### 2.2 Architectural Gaps

| # | Gap | Severity | Description & Risk |
|---|-----|----------|--------------------|
| **A1** | No Formal API Contracts | 🔴 HIGH | Interfaces between CROP↔CRDS, CROP↔OMOS, CROP↔LIPL, CROP↔CRM are described in natural language only. No schema, OpenAPI spec, or message contract defined. |
| **A2** | No Dead-Letter Queue / Error Store | 🔴 HIGH | No mention of error storage for failed CRDS/OMOS calls. Without a DLQ, failed portfolios may silently drop. |
| **A3** | Document State Machine Not Formalized | 🔴 HIGH | The document lifecycle (Scheduled → Payload Requested → Generated → Released) is implicit in the description. A formal state machine is needed to avoid inconsistent document states in the database. |
| **A4** | Batch Concurrency Not Addressed | 🔴 HIGH | Can ME+1, ME+2, ME+3 run concurrently? What is the locking strategy to prevent the same portfolio from being processed by two concurrent batch runs? |
| **A5** | Authentication & Authorization Model | 🔴 HIGH | No mention of how users authenticate (SSO/LDAP) or what role-based access controls exist for different screens (Operations vs Business User vs Reviewer vs Admin). |
| **A6** | CRDS Communication Pattern | 🔴 HIGH | Is the CRDS payload request synchronous REST or async (event/queue)? This fundamentally affects CROP's batch architecture, timeout handling, and scalability. |
| **A7** | OMOS Callback Mechanism | 🟠 MEDIUM | Does OMOS call back to CROP when a document is generated (webhook/event), or does CROP poll OMOS? Not defined. |
| **A8** | Scalability / Parallelism Strategy | 🟠 MEDIUM | For large portfolio volumes, the batch must process portfolios in parallel. The degree of parallelism, thread pool sizing, and back-pressure strategy are not addressed. |
| **A9** | Data Retention & Archival | 🟠 MEDIUM | Document payload data, generated document references, audit logs — no retention policy defined. Financial regulatory requirements typically mandate 7–10 years. |
| **A10** | Versioning Strategy | 🟡 LOW | As a hub system with multiple integrations, CROP needs an API versioning strategy to allow dependent systems to upgrade independently. |

### 4.3 Batch Process Flow — Bank Entity (JWM Bank)

> **Key rule**: No price availability check for Bank entity. Batch runs on ME+1 through ME+4.

```mermaid
sequenceDiagram
    participant SCH as Scheduler
    participant BATCH as Batch Engine (CROP)
    participant CRM as CRM
    participant LIPL as LIPL
    participant CRDS as CRDS
    participant ORCH as Document Orchestrator
    participant OMOS as OMOS
    participant AUDIT as Audit Service

    SCH->>BATCH: Trigger ME+N batch (entity=BANK, period=YYYY-MM)
    AUDIT->>AUDIT: Log batch started (batch_id, entity, period, trigger_time)

    BATCH->>CRM: GET active portfolios (entity=BANK)
    CRM-->>BATCH: [ {portfolio_id, client_id, doc_types[], ...} ]

    BATCH->>LIPL: GET delivery instructions (portfolio_ids[])
    LIPL-->>BATCH: [ {portfolio_id, frequency, address, language, currency} ]

    BATCH->>BATCH: Filter by schedule & frequency (skip if not due this ME+N)

    loop For each eligible portfolio (parallelized)
        BATCH->>BATCH: Check idempotency (doc state NOT in GENERATED/RELEASED?)
        alt Document already generated/released
            BATCH->>AUDIT: Log SKIPPED (idempotent)
        else Not yet generated
            BATCH->>CRDS: POST /payload/request {portfolio_id, doc_type, period, entity}
            alt CRDS success
                CRDS-->>BATCH: Document payload
                BATCH->>ORCH: Submit (portfolio_id, payload, delivery_instructions)
                ORCH->>OMOS: POST /generate {portfolio_id, payload, metadata}
                OMOS-->>ORCH: {document_id, status: GENERATED}
                ORCH->>BATCH: GENERATED
                BATCH->>AUDIT: Log SUCCESS (portfolio_id, doc_id, doc_type)
            else CRDS failure / timeout
                CRDS-->>BATCH: Error / Timeout
                BATCH->>BATCH: Retry (max 3, exponential backoff)
                BATCH->>AUDIT: Log PAYLOAD_FAILED → DLQ
                NOTIF->>NOTIF: Alert ops team
            end
        end
    end

    AUDIT->>AUDIT: Log batch completed (total, success, skipped, failed)
```

### 4.4 Batch Process Flow — JV Entity (Securities, with Price Check)

> **Key rule**: If any instrument in a portfolio has no valid month-end price, the portfolio is DEFERRED for that ME+N run. Price acceptance by ops user unblocks it.

```mermaid
sequenceDiagram
    participant SCH as Scheduler
    participant BATCH as Batch Engine (CROP)
    participant CRM as CRM
    participant LIPL as LIPL
    participant PRICE as Price Check Service
    participant CRDS as CRDS
    participant ORCH as Document Orchestrator
    participant OMOS as OMOS
    participant AUDIT as Audit Service

    SCH->>BATCH: Trigger ME+N batch (entity=JV, period=YYYY-MM)
    BATCH->>CRM: GET active portfolios (entity=JV)
    CRM-->>BATCH: Portfolio list (JV)
    BATCH->>LIPL: GET delivery instructions
    LIPL-->>BATCH: Delivery instructions

    loop For each eligible JV portfolio
        BATCH->>PRICE: GET price readiness (portfolio_id, period)
        PRICE->>PRICE: Fetch instruments with positions\nfor this portfolio
        PRICE->>PRICE: Check each instrument:\nlatest price date vs month-end date

        alt All instruments have valid month-end prices
            PRICE-->>BATCH: {status: READY}
            BATCH->>CRDS: POST /payload/request
            CRDS-->>BATCH: Document payload
            BATCH->>ORCH: Submit to OMOS
            ORCH->>OMOS: POST /generate
            OMOS-->>ORCH: GENERATED
            BATCH->>AUDIT: Log SUCCESS
        else Some instruments have stale/missing prices
            PRICE-->>BATCH: {status: NOT_READY, instruments: [{isin, latest_price_date, gap_days}]}
            BATCH->>BATCH: Mark portfolio as DEFERRED
            BATCH->>AUDIT: Log DEFERRED (portfolio_id, missing instruments list)
            Note over BATCH: Portfolio visible on Readiness Screen (S2)\nUser reviews on Price Screen (S1) and can accept price
        else All instruments have ops-accepted prices
            PRICE-->>BATCH: {status: READY, note: "accepted_prices_used"}
            BATCH->>CRDS: POST /payload/request (with accepted price flag)
            BATCH->>AUDIT: Log SUCCESS (price_acceptance_used=true)
        end
    end
```

### 4.5 Price Acceptance Flow — Operations User (JV)

```mermaid
sequenceDiagram
    participant OPS as Operations User
    participant S1 as Price Review Screen (CROP)
    participant PRICE as Price Check Service
    participant STORE as Price Acceptance Store
    participant AUDIT as Audit Service
    participant BATCH as Next Batch Run

    OPS->>S1: Navigate to Price Review Screen\n(filtered by period, entity=JV)
    S1->>PRICE: GET /portfolios/readiness?period=YYYY-MM&entity=JV
    PRICE-->>S1: [{portfolio_id, status, instruments: [{isin, name, latest_price, price_date, days_from_me}]}]
    S1-->>OPS: Display portfolio grid with price status

    OPS->>S1: Click portfolio row (status=NOT_READY)
    S1-->>OPS: Show instrument detail:\nISIN | Name | Latest Price | Price Date | Days from ME | Source | Action

    OPS->>S1: Click "Accept as Month-End Price" for instrument(s)
    S1->>S1: Show confirmation modal:\n"Accept price [X] dated [D] as month-end price for [ISIN]?"

    OPS->>S1: Confirm acceptance
    S1->>STORE: POST /prices/accept\n{instrument_id, price, price_date, period, portfolio_id, entity}

    alt Acceptance succeeds (no conflict)
        STORE-->>S1: {acceptance_id, status: ACCEPTED}
        S1->>AUDIT: POST /audit\n{user_id, action: PRICE_ACCEPTED, instrument_id, price, price_date, timestamp}
        AUDIT-->>S1: {audit_ref}
        S1-->>OPS: Success toast — "Price accepted. Instrument marked READY."
        S1->>S1: Refresh portfolio readiness status
    else Conflict (another user accepted concurrently)
        STORE-->>S1: 409 Conflict
        S1-->>OPS: Error — "Price already accepted by [user]. Refresh to see latest state."
    end

    Note over BATCH: On next ME+N batch run
    BATCH->>PRICE: GET price readiness (portfolio_id, period)
    PRICE->>STORE: Check accepted prices for period
    STORE-->>PRICE: Accepted price exists for all instruments
    PRICE-->>BATCH: {status: READY, accepted_prices_used: true}
    BATCH->>BATCH: Proceed with document generation
```

### 4.6 Document Lifecycle State Machine

```mermaid
stateDiagram-v2
    [*] --> SCHEDULED : Batch trigger (ME+N) or Ad-hoc request

    SCHEDULED --> PRICE_CHECK : Entity = JV (periodic only)
    PRICE_CHECK --> PAYLOAD_REQUESTED : All prices READY
    PRICE_CHECK --> DEFERRED : Prices NOT_READY
    DEFERRED --> SCHEDULED : Next ME+N batch re-evaluates price readiness
    DEFERRED --> PAYLOAD_REQUESTED : (Ad-hoc bypass — no price check)

    SCHEDULED --> PAYLOAD_REQUESTED : Entity = BANK (skip price check)\nOR Ad-hoc request

    PAYLOAD_REQUESTED --> PAYLOAD_RECEIVED : CRDS responds with payload
    PAYLOAD_REQUESTED --> PAYLOAD_FAILED : CRDS error / timeout (after retries)
    PAYLOAD_FAILED --> PAYLOAD_REQUESTED : Manual retrigger via S3\nOR next ME+N batch

    PAYLOAD_RECEIVED --> SUBMITTED_TO_OMOS : Document Orchestrator submits to OMOS
    SUBMITTED_TO_OMOS --> GENERATED : OMOS generates PDF successfully
    SUBMITTED_TO_OMOS --> GENERATION_FAILED : OMOS error (after retries)
    GENERATION_FAILED --> SUBMITTED_TO_OMOS : Manual retrigger via S3

    GENERATED --> UNDER_REVIEW : Reviewer opens document in OMOS
    UNDER_REVIEW --> RELEASED : Reviewer approves and releases
    UNDER_REVIEW --> REGENERATION_REQUESTED : Reviewer rejects document
    REGENERATION_REQUESTED --> SCHEDULED : Re-enters pipeline (new version)

    RELEASED --> DELIVERED_EDOC : Channel = Client eDocuments
    RELEASED --> DELIVERED_PRINT : Channel = Printer
    RELEASED --> DELIVERED_ARCHIVE : Channel = UBS Archive
    RELEASED --> DELIVERED_MULTI : Channel = Multiple (e.g., eDoc + Archive)

    DELIVERED_EDOC --> [*]
    DELIVERED_PRINT --> [*]
    DELIVERED_ARCHIVE --> [*]
    DELIVERED_MULTI --> [*]

    note right of DEFERRED
        Visible on Portfolio Readiness Screen (S2)
        Operations can accept prices on Price Review Screen (S1)
        to unblock next batch run
    end note

    note right of GENERATED
        Documents tagged: PERIODIC or AD-HOC
        Ad-hoc documents carry visual indicator
        in OMOS (no price check performed)
    end note
```

    ADHOC-->>S5: {request_id, status: GENERATED, doc_id}

## 7. Architecture Decision Records (ADRs)

> Each ADR follows the format: Context → Options → Decision → Consequences.

---

### ADR-001 — Batch Portfolio Processing: Synchronous vs Asynchronous

| Field | Detail |
|-------|--------|
| **Status** | Proposed |
| **Deciders** | Architecture Team |
| **Context** | CROP requests CRDS payloads for potentially thousands of portfolios per batch run. The communication strategy directly impacts throughput, latency, and resilience. |
| **Options** | **A**: Synchronous REST — CROP waits per portfolio (simple, brittle at scale). **B**: Async message queue — CROP publishes requests; CRDS publishes payloads back (resilient, higher complexity). **C**: Batch API — CROP sends portfolio batch; CRDS responds with batch payload (balanced). |
| **Decision** | **Option B or C** (to be confirmed after Q3 clarification on CRDS protocol). Prefer async to avoid batch timeout failures on large volumes. |
| **Consequences** | Requires message broker (Kafka/RabbitMQ) or CRDS batch endpoint. DLQ required. Increases operational complexity but improves resilience significantly. |

---

### ADR-002 — Idempotent Batch Execution

| Field | Detail |
|-------|--------|
| **Status** | Proposed |
| **Context** | ME+N batches may be re-triggered due to failures or manual retrigger. Duplicate document generation would be a serious financial data integrity issue. |
| **Decision** | Define a natural key per document: `(portfolio_id, doc_type, entity, period)`. Before processing any portfolio, CROP checks if a document with this key already exists in a terminal state (`GENERATED`, `RELEASED`). If yes → skip. If in `FAILED` → retrigger last failed step. Enforce unique constraint on natural key in Document State DB. |
| **Consequences** | Requires schema-level unique constraint. Batch engine must query document state before submission. Idempotency check adds minor overhead per portfolio. |

---

### ADR-003 — Document State Management: State Column vs Event Sourcing

| Field | Detail |
|-------|--------|
| **Status** | Proposed |
| **Context** | Documents go through a well-defined lifecycle with audit, retry, and replayability requirements. Financial regulatory audit trails require full history. |
| **Options** | **A**: State column in relational DB (simple, no full history). **B**: Append-only state transition log (full history, queryable). **C**: Full event sourcing (maximum auditability, highest complexity). |
| **Decision** | **Option B** — Append-only state transition table (`document_state_events`) alongside a current-state view table. Provides full history without full event sourcing complexity. Each transition record: `doc_id, from_state, to_state, triggered_by, timestamp, reason`. |
| **Consequences** | Slightly more complex queries; full audit history available for compliance. Supports retrigger and regeneration logic cleanly. |

---

### ADR-004 — Entity Separation: Bank vs JV as First-Class Concept

| Field | Detail |
|-------|--------|
| **Status** | Accepted |
| **Context** | Bank and JV entities have materially different processing rules. Mixing entity logic risks cross-contamination of price checks, scheduling, and document states. |
| **Decision** | `entity` (`BANK` / `JV`) is a mandatory, non-nullable field on every core domain object: portfolios, document states, schedules, price records, batch runs. All processing logic is branched by entity at the topmost level. Price availability service is invoked if and only if `entity == JV`. This must be enforced as an invariant in the codebase. |
| **Consequences** | All DB schemas, APIs, and UI filters must include entity as a mandatory discriminator. Prevents entity leakage. |

---

### ADR-005 — Price Acceptance Concurrency Control

| Field | Detail |
|-------|--------|
| **Status** | Proposed |
| **Context** | Multiple operations users may attempt to accept prices for the same instrument in the same period concurrently. Acceptance must be idempotent and the first write must win. |
| **Decision** | Implement **optimistic locking** on price acceptance. Price acceptance record carries a version field. First write wins; subsequent concurrent write returns HTTP 409 Conflict. Natural key: `(instrument_id, period, entity)`. UI must handle 409 gracefully, refresh the state, and display a friendly message indicating the instrument was already accepted. |
| **Consequences** | UI must implement conflict handling. Prevents double-acceptance. Audit log captures which user's acceptance was persisted. |

---

### ADR-006 — Role-Based Access Control (RBAC) Model

| Field | Detail |
|-------|--------|
| **Status** | Proposed |
| **Context** | CROP screens have different sensitivity and user types. Without RBAC, any user could release documents to clients or accept prices. |
| **Decision** | Define four roles: `OPERATIONS` (S1, S2 — JV price screens), `BUSINESS_USER` (S2, S3, S5), `REVIEWER` (S3 — release only), `ADMIN` (all screens + S4). Integrate with enterprise SSO/LDAP. All API endpoints enforce role-based authorization. Ad-hoc generation (S5) restricted to `BUSINESS_USER` minimum. Price acceptance (S1) restricted to `OPERATIONS`. |
| **Consequences** | Requires SSO/LDAP integration. Each API endpoint must validate the caller's role. Screen-level navigation driven by role. |

---

### ADR-007 — Ad-hoc Generation: Price Check Bypass Governance

| Field | Detail |
|-------|--------|
| **Status** | Proposed |
| **Context** | Ad-hoc requests bypass price availability checks. This is a deliberate business decision but risks producing documents with stale or missing prices without oversight. |
| **Decision** | Ad-hoc generation bypasses price checks but: (1) Requires `BUSINESS_USER` or `ADMIN` role minimum. (2) User must provide a reason/justification (mandatory free-text). (3) System logs `PRICE_CHECK_BYPASSED = true` in the audit record. (4) Generated documents are tagged with source `AD-HOC` in OMOS, with a visible indicator in the document review UI. |
| **Consequences** | OMOS must support document source tagging. Audit log captures bypass justification. Provides traceability without blocking legitimate ad-hoc use cases. |

---

### ADR-008 — Frequency Conflict Resolution: LIPL vs CROP Config

| Field | Detail |
|-------|--------|
| **Status** | Proposed |
| **Context** | LIPL provides delivery frequency per portfolio. CROP also configures schedule. For balance certificates, CROP overrides LIPL. Conflict resolution is currently undefined. |
| **Decision** | Establish explicit frequency ownership per document type: **Balance Certificate** → CROP is owner (CROP config takes precedence; LIPL ignored). **Account Statement** → LIPL is owner (LIPL value used; CROP as fallback if LIPL returns null). **Performance Report** → LIPL is owner (same as Account Statement). This ownership matrix must be version-controlled in CROP config and documented in code. |
| **Consequences** | Config service must model "owned" vs "delegated" frequency per document type. Changes to ownership require a config update, not a code change. |

---

### ADR-009 — Retry Strategy for External Integration Failures

| Field | Detail |
|-------|--------|
| **Status** | Proposed |
| **Context** | CRDS (payload) and OMOS (generation) are external systems that can fail. Unbounded retries cause resource exhaustion; no retries cause silent data loss. |
| **Decision** | **CRDS payload request**: Exponential backoff, max 3 attempts, then mark `PAYLOAD_FAILED`, write to DLQ, alert ops. **OMOS generation**: Max 2 retries, then mark `GENERATION_FAILED`, write to DLQ, alert ops. Manual retrigger available via Document Management Screen (S3). DLQ monitored by ops with SLA for resolution. |
| **Consequences** | DLQ infrastructure required. Ops runbook needed for DLQ triage. Alert integration required (see ADR-010). |

---

### ADR-010 — Observability, Monitoring, and Alerting Strategy

| Field | Detail |
|-------|--------|
| **Status** | Proposed |
| **Context** | CROP is a mission-critical financial batch system. Without observability, failures in month-end processing may go undetected until client complaint. |
| **Decision** | Implement: (1) **Structured logging** for all batch events (batch_id, portfolio_id, state, error). (2) **Metrics** (Prometheus-compatible): `batch_run_duration_seconds`, `portfolios_processed_total`, `portfolios_deferred_total`, `documents_generated_total`, `documents_failed_total`, `price_acceptances_total`. (3) **Dashboards** (Grafana or equivalent) per entity. (4) **Alerts**: Batch failure → immediate; Error rate > 5% → warn; DEFERRED count > threshold after ME+3 → warn; DLQ depth > 0 → alert. |
| **Consequences** | Requires logging/monitoring infrastructure. Ops dashboard and runbook required. Alert thresholds must be calibrated after go-live. |

---

### ADR-011 — GSM Price Upload Validation for Structured Instruments

| Field | Detail |
|-------|--------|
| **Status** | Proposed |
| **Context** | Operations manually upload structured bond and fund prices to GSM. Erroneous prices propagating to CRDS would corrupt generated statements with no automated safeguard. |
| **Decision** | GSM file upload process (or a CROP-side validation step post-feed) must apply: (1) Price range check (> 0, within ± X% of prior month price — configurable threshold). (2) Duplicate detection (same instrument + same date). (3) Ops approval gate before prices propagate to CRDS (if feasible within GSM workflow). If validation is outside CROP's scope, CROP should at minimum log a warning when accepted price deviates significantly from prior period. |
| **Consequences** | Scope clarification needed: does this validation live in GSM or CROP? If CROP, adds complexity to price check service. |
